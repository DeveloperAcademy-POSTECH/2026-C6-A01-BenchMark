# BenchMark PRD 초안

- 버전: v0.1
- 작성일: 2026-09-08
- 상태: 검토용 초안 — 제품 범위 및 기관 협의 미확정
- 목적: 누구를 위해 무엇을 만들고, 어떤 조건에서 파일럿을 진행할지 합의한다.

## 1. 문서의 근거와 전제

현재 저장소에는 README의 Git 운영 규칙만 있으며 앱 코드, 기술 스택, 제품 요구사항, 테스트 및 배포 설정은 없다. 이 문서는 2026-08-19~27의 BenchMark 기획·리서치 작업 기록을 참고해 작성했다. 당시 Miro와 기획서의 내용은 이번 작성 시점에 원본을 다시 확인하지 않았으므로 최신 결정과 다를 수 있다.

- 이전 기획 방향: POSTECH의 기억이 있는 장소에 기부하고, 벤치 등 실제 휴식공간으로 이어지는 경험.
- 이전 타깃 정의: 최근 POSTECH 발전기금 기부 경험 또는 향후 12개월 내 기부 의향이 있고, 캠퍼스 장소에 개인적 기억이 있는 동문.
- 이전 채널 후보: 현장 QR/NFC, 웹, App Clip, iOS 앱.
- 이 초안의 제안: 기관이 승인한 소수 프로젝트를 대상으로 정보 탐색, 참여 연결, 진행 확인, 설치 결과 확인을 우선 검증한다.

아래 요구사항은 구현 완료 상태나 확정된 기관 약속을 의미하지 않는다. 새로 제안한 범위와 검증 기준은 승인 전까지 변경 가능하다. 결제 불편, 앱 설치 수요, 반복 방문 수요를 검증된 문제로 단정하지 않는다.

## 2. 제품 정의

**BenchMark는 동문이 캠퍼스의 기억을 실제 공간에 남길 수 있도록, 기부 참여부터 벤치 조성 결과 확인까지 연결하는 서비스다.**

가치는 ‘기억을 남기는 것’, 참여 수단은 ‘기부’, 결과물은 ‘벤치 등 실제 공간’, 디지털 서비스는 ‘그 과정을 연결하는 수단’으로 정의한다. 최초 파일럿은 벤치에 집중하되 다른 시설로의 확대를 위해 미리 복잡한 범용 시스템을 만들지는 않는다.

### 문제 가설

1. 기부 의향이 있는 동문이 자신의 기억과 연결되는 구체적인 사용처를 선택하기 어렵다.
2. 참여자가 조성 진행 상황, 설치 결과, 이후 관리 책임을 한곳에서 확인하기 어렵다.
3. 운영자가 참여 문의와 진행 안내를 여러 도구로 처리하면서 같은 정보를 반복 전달할 수 있다.

검증 시 실제 최근 경험, 기존 도구, 발생한 시간 손실, 우회 방법을 수집한다. 아이디어에 대한 호감만으로 문제나 앱 수요가 확인됐다고 판단하지 않는다.

## 3. 사용자와 핵심 과업

| 사용자 | 핵심 과업 | 제공 가치 |
| --- | --- | --- |
| 1차: POSTECH 동문 기부 의향자·기부자 | 기억이 있는 장소의 프로젝트를 이해하고 참여한 뒤 결과를 확인한다. | 구체적 사용처, 참여 방법, 신뢰할 수 있는 완료 증거 |
| 2차: 발전기금 담당자 | 승인된 참여 경로를 안내하고 프로젝트 현황을 전달한다. | 일관된 안내와 문의 처리 기준 |
| 운영: 시설 담당자 | 설치 가능성, 일정, 완료 및 유지관리 정보를 제공한다. | 공개 정보와 실제 시설 상태의 일치 |
| 보조: 현장 방문자 | 벤치의 의미와 공개된 이야기를 읽는다. | 공간과 기부 배경에 대한 이해 |

공동기부 대표자의 조율 업무는 추가 검증 대상으로 둔다. 일반 시민·재학생·기업을 위한 별도 모금 흐름은 최초 MVP 범위에서 제외한다.

### 대표 사용자 이야기

- 동문으로서 후보 장소와 조성 목적을 보고 내가 기여할 공간을 선택하고 싶다.
- 참여자로서 내가 참여한 프로젝트의 현재 단계와 변경 사유를 확인하고 싶다.
- 기부자로서 실제 설치 사진, 설치일, 위치, 관리 주체를 확인하고 싶다.
- 운영자로서 확인된 정보만 공개하고 잘못된 내용을 수정한 기록을 남기고 싶다.

## 4. 목표와 비목표

### 목표

- 장소·목적·참여 방법·관리 주체를 이해한 상태에서 기부 여부를 결정할 수 있다.
- 참여 안내, 조성 진행 상황, 설치 결과가 하나의 프로젝트에 연결된다.
- 기관이 제공할 수 있는 자료와 운영 인력으로 실제 갱신이 가능한 구조를 만든다.
- 디지털 서비스가 기존 공식 페이지·메신저·문서 대비 도움이 되는지 파일럿으로 확인한다.

### 이번 MVP의 비목표

- 자체 결제 처리, 자금 보관·정산, 기부금영수증 발급 시스템 구축
- 기관 승인 전 공개 모금 또는 설치 장소 확약
- 전국 대학 대상 모금 플랫폼 및 기업 후원 상품
- AR, 음악, 소셜 피드, 순위, 포인트를 통한 참여 유도
- 웹·App Clip·iOS 앱을 동시에 완성하는 다중 채널 출시

## 6. 핵심 흐름과 상태

### 참여 흐름

1. 사용자가 프로젝트 목록 또는 공유 링크로 진입한다.
2. 장소, 조성 목적, 진행 단계, 기관, 관리 책임을 확인한다.
3. 공식 참여 경로로 이동해 해당 기관의 절차를 따른다.
4. 서비스로 돌아와 프로젝트 진행과 설치 결과를 확인한다.

공식 기관의 확인 데이터가 없는 경우 개인의 기부 여부·금액을 서비스가 추정하지 않는다. 기관 연동이 없더라도 공개 프로젝트의 진행 확인은 가능해야 한다.

### 운영 흐름

`초안 → 기관 검토 → 공개/참여 안내 → 조성 중 → 설치 완료 → 유지관리`

- 반려된 초안은 사유를 기록하고 수정 후 재검토한다.
- 공개 이후 지연·중단·취소가 발생하면 실제 상태와 사유, 갱신일, 문의 경로를 표시한다.
- 참여 종료와 설치 완료는 별개다. 참여가 끝났다고 설치 완료로 전환하지 않는다.
- 모금 목표·달성액은 기관이 제공하고 검증할 수 있을 때만 공개한다. 자료가 없으면 수치 영역을 숨긴다.
- 목표 미달, 위치 변경, 취소 시 자금 처리 안내는 기관이 승인한 정책만 사용한다.

## 7. 정보 구조와 데이터 요구사항

기본 정보 구조는 프로젝트 목록, 프로젝트 상세, 진행 기록, 설치 결과, 문의·운영 안내로 구성한다. 계정·내 참여 화면은 개인별 참여 확인 필요성이 검증된 경우에 추가한다.

| 개념 | 필요한 정보 | 처리 원칙 |
| --- | --- | --- |
| Project | 식별자, 제목, 목적, 장소, 단계, 운영 기관, 참여 URL, 갱신일 | 공개 승인 상태와 조성 상태를 구분한다. |
| ProgressUpdate | 프로젝트, 단계, 내용, 발생일, 작성자, 승인 정보 | 사용자에게 실제 발생일과 갱신일을 혼동시키지 않는다. |
| InstallationEvidence | 프로젝트, 설치일, 위치, 사진, 확인자, 관리 주체 | 완료 공개의 필수 근거로 사용한다. |
| PublicStory | 프로젝트, 공개 이름, 이야기, 공개 동의·검토 상태 | P1. 연락처와 공개 콘텐츠를 분리한다. |
| AuditRecord | 변경 대상, 작업자, 변경 시각, 변경 내용 | 운영 변경과 승인 이력을 추적한다. |

이는 논리적 데이터 요구사항이며 특정 데이터베이스 스키마나 백엔드 선정이 아니다. 개인별 기부 기록·금액·연락처는 수집 목적과 기관 데이터 제공 범위가 확정되기 전까지 MVP 필수 데이터로 두지 않는다.

## 8. 품질 및 운영 요구사항

- 신뢰성: 단계별 출처와 갱신일을 제공하고, 마지막 확인 상태를 유지한다. 조회 실패를 프로젝트 취소나 데이터 없음으로 대체하지 않는다.
- 보안: 공개 조회와 운영 변경 권한을 분리하고, 운영 권한은 서버에서 검증한다. 비공개 초안과 개인정보는 공개 응답에 포함하지 않는다.
- 개인정보: 공개 이름·사진·이야기는 공개 범위에 동의한 자료만 사용한다. 삭제·정정 요청 경로를 마련한다.
- 접근성: 텍스트 확대, 보조기술 탐색, 충분한 대비를 지원하고 색만으로 단계를 구분하지 않는다.
- 권한: 위치·카메라 권한 없이 목록·상세·참여 안내를 이용할 수 있다.
- 실패 대응: 외부 참여 경로 장애 시 재시도 및 공식 문의 경로를 제공한다. 기부 성공 여부를 임의로 표시하지 않는다.
- 운영 지속성: 정보 갱신 담당자와 주기를 정하고, 담당자 변경 시 프로젝트 운영 정보를 인계할 수 있어야 한다.

Needs confirmation: 지원 플랫폼·최소 OS·성능 목표·가용성 목표·데이터 보관 기간·백업/복구 기준은 기술 및 운영 범위 확정 후 수치와 책임자를 정한다.

## 9. 검증 계획과 성공 기준

### 문제 검증

- 타깃 동문에게 최근 기부 결정과 결과 확인 행동을 질문한다.
- 발전기금·시설 담당자에게 현재 안내·승인·업데이트 절차와 제공 가능한 데이터를 확인한다.
- 공동기부를 우선할 경우 대표자의 메신저·폼·스프레드시트 사용 과정에서 실제 누락과 반복 작업을 조사한다.
- 기관이 참여 연결, 설치, 결과 공개, 유지관리 책임을 수용할 수 있는지 먼저 확인한다.

### 사용성 검증 기준 제안

- 타깃 사용자 5명 중 4명 이상이 도움 없이 프로젝트의 장소·현재 단계·참여 경로를 찾는다.
- 5명 중 4명 이상이 참여 안내와 설치 완료를 정확하게 구분한다.
- 운영자가 프로젝트를 등록하고 진행 변경·설치 완료 증거를 공개하는 흐름을 수행한다.
- 실패·지연·취소 시 사용자가 현재 상태와 문의 경로를 이해한다.

이는 소규모 사용성 점검 기준이며 시장 수요를 입증하는 통계 기준이 아니다.

### 파일럿 측정 지표

| 지표 | 정의 | 해석 시 주의 |
| --- | --- | --- |
| 참여 경로 이동률 | 기간 내 공식 참여 링크를 누른 고유 세션 / 상세를 조회한 고유 세션 | 실제 기부 전환율로 부르지 않는다. |
| 진행 재방문율 | 최초 상세 조회 이후 30일 내 진행·결과 화면을 다시 본 식별 가능 사용자 / 30일 관찰 가능한 최초 조회 사용자 | 동의·식별 방식이 없으면 측정하지 않는다. |
| 완료 증거 충족률 | 필수 완료 자료가 모두 있는 설치 완료 프로젝트 / 설치 완료 프로젝트 | 분모가 0이면 미측정으로 표시한다. |
| 운영 갱신 소요 시간 | 기관의 변경 확인부터 서비스 공개까지 걸린 시간 | 담당자 확인과 승인 시간을 포함한다. |

Needs confirmation: 분석 동의·식별 방식, 지표별 목표치, 파일럿 기간·규모는 합의가 필요하다. 실제 기부 전환은 기관이 제공할 수 있는 확인 데이터가 있을 때만 별도로 측정한다.

## 10. 실행 단계와 출시 조건

| 단계 | 산출물 | 다음 단계 조건 |
| --- | --- | --- |
| 1. 범위 합의 | 타깃, 기부 유형, 채널, 기관 역할, 비용·운영 조건 | 기관 협의의 차단 조건 해소 |
| 2. 문제·흐름 검증 | 인터뷰 기록, 기존 도구 비교, 주요 화면 프로토타입 | 반복되는 문제와 흐름 이해 확인 |
| 3. MVP 구현 | P0 흐름, 운영 절차, 접근 권한, 예외 처리 | 기능·권한·사용성 검증 통과 |
| 4. 제한 파일럿 | 승인된 실제 프로젝트, 업데이트 기록, 측정 결과 | 사용자 가치와 운영 가능성 확인 |
| 5. 유지·확대 판단 | 개선안 및 후속 범위 | POSTECH 내 운영 검증 후 과학기술특성화대학, 일반 대학 순으로 검토 |

이전 기획의 9~11월 일정은 현재 확정 일정으로 채택하지 않는다. 담당자·기관 승인·개발 범위가 정해진 뒤 실제 날짜를 배정한다.

### 파일럿 출시 체크리스트

- [ ] 기관의 프로젝트 공개 및 참여 경로 승인이 있다.
- [ ] 설치 장소·비용 부담·유지관리 담당과 변경·취소 안내가 합의됐다.
- [ ] P0 요구사항과 권한·비공개 데이터 노출 검증이 통과했다.
- [ ] 실제 승인 자료로 프로젝트를 등록하고 변경·완료 공개 흐름을 확인했다.
- [ ] 장애·지연·취소·외부 링크 실패를 검증했다.
- [ ] 핵심 흐름의 접근성과 타깃 사용자 사용성 점검을 완료했다.
- [ ] 문의 담당자, 정보 갱신 주기, 정정 절차가 정해졌다.
