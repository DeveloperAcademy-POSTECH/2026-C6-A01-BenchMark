# 기부 증빙 의미 판정 v3

2026-11-05 사용자 요청 / #161·PR #162. 문자·이체 내역·기부 영수증의 **근거 충분성**을 판정한다. 공식 영수증은 필수가 아니다. 2026-11-08 / #234부터 증빙은 선택 제출이며, AI 참고 검사나 운영자 검토에서 작성 권한을 부여하지 않는다.

## 판정 구조

기존 Responses API 문서 전송·형식 검증을 재사용하되, 사용자용 함수는 `donation-assessment.ts`의 별도 구조화 추출과 서버 규칙을 사용한다. 운영자용 시각 검사·학교 증빙 검사 계약은 유지한다. 모델이나 응답 프롬프트가 직접 `approved`를 결정하지 않는다.

1. 모델은 문서 종류, 보이는 기관, 약정/예정/완료/취소, 실제 발신 헤더와 본문 번호 구분, 명시적 완료 근거, 날짜·수정 흔적, 존재할 때만 고유 거래 참조를 추출한다.
2. 서버가 공식 출처의 확인일·기관·발신번호·입금 완료 의미·가독성·모순·중복 검사 결과를 조합해 판정한다. 날짜 비교는 한국 시간 기준이다.
3. 결과는 `sufficient_evidence`, `needs_more_evidence`, `manual_review`, `suspected_manipulation`, `duplicate_evidence`, `not_donation` 중 하나다. `summary.sufficient_evidence`와 판정이 일치해야 한다.
4. 충족 결과도 `human_review_required: true`, `authenticity_verified: false`, `writing_permission_granted: false`다. 마지막 필드는 구형 클라이언트 호환용이다. 증빙 결과는 이야기의 작성이나 공개에 영향을 주지 않는다.

## 문자의 충족 조건

실제 발신 헤더 번호가 공식 POSTECH 문의 번호와 일치하고, 기관 표기와 명시적 기부 입금 완료 내용이 보이며, 판독 가능한 자료에 구체적 수정·날짜 모순·중복 근거가 없으면 문자만으로 `증빙 충족`이 가능하다. 같은 이력에 약정 접수와 그 뒤의 입금 확인이 함께 있으면 마지막 입금 근거를 구분한다. 나중의 취소·환불도 확인한다.

`054-279-2417`은 공식 **문의 번호**로 대조한다. SMS 발신 인증이 등록됐다고 주장하지 않는다. `+82 54-279-2417`을 국내 형식으로 정규화한다. 본문 연락처·저장된 연락처 이름만 일치하거나, 수신전용 약정 번호 `1800-2547`인 경우 발신 확인으로 인정하지 않는다.

약정 접수·납부 예정·예약·입금 부정 문구·취소는 완료로 취급하지 않는다. 이름 가림, 금액 부재, 연도 없는 SMS 날짜 자체는 반려 사유가 아니다. 다른 기관/미확인 기관은 POSTECH 기준을 억지로 적용하지 않고 추가 확인한다. 은행 이체는 메모가 아닌 실제 수취기관과 완료 상태를 확인한다.

공식 안내·공개 기부 사례는 출처를 구분해 모델과 결과에 제공한다. 확인된 타 기부자 SMS 원본이 없으므로 정상 후기 일치를 꾸며내지 않는다. [출처 검토](donation-evidence-source-review.md)에 확인된 근거와 확보하지 못한 자료를 명시한다.

## 중복 검사와 비공개 저장

`benchmark_private.oi_evidence_fingerprints`는 신청 ID·제출 시각·파일 SHA-256·선택적인 거래 HMAC만 저장한다. 원본 문자·거래번호·이름·금액을 이 장부에 저장하지 않는다.

- 동일 파일의 다른 신청 재사용과, 바이트가 달라도 충분한 자료에서 읽힌 고유 거래 참조 재사용을 검사한다.
- 일반 사용자는 장부를 읽거나 지문을 등록할 수 없다. 함수가 JWT와 canonical 계정의 현재 신청을 확인한 후 service-role 전용 RPC를 호출한다.
- RPC는 현재 소유자·경로·제출 시각을 다시 확인하고 동일 지문 등록을 직렬화한다. 동시 제출 두 건이 모두 신규로 통과하는 경합을 막는다.
- 같은 신청 재검사는 중복으로 보지 않는다. 같은 제출본에서 재검사 중 거래번호 추출이 누락돼도 기존 지문을 지우지 않는다. 파일/제출 버전 교체 시 이전 지문을 제거한다.
- 공통 감사 문구·날짜·금액만·문의 번호·약정 ID는 거래 지문이 아니다. 다른 기부자가 같은 문자 양식을 받았다는 이유로 중복 처리하지 않는다.
- 지문용 전용 키는 기존 Supabase Vault의 `oi_evidence_fingerprint_key`에 서버가 생성한다. service-role 전용 getter를 통해 메모리에서만 사용하며 클라이언트·로그·명령 인자에 노출하지 않는다. 일반 서비스 키 회전과 분리된다.
- 전용 Vault 키를 삭제/교체하면 과거 거래 HMAC과 신규 HMAC의 매칭이 끊긴다. 원문을 장부에 저장하지 않으므로 재계산에는 원본 재검사가 필요하다. 파일 SHA 중복 검사는 영향을 받지 않는다.

이 검사는 임의 잘라내기·재촬영·고유 거래 정보 삭제를 모두 탐지하는 이미지 포렌식이 아니다. 모르는 것을 위조 확정으로 표현하지 않는다. 분석을 거친 현재 장부 범위가 기준이며, 도입 이전 모든 파일이 자동 역색인되는 것은 아니다.

## 검증

- `node --test supabase/tests/*.test.mjs`: 의미 규칙·추출 계약·기존 분석 회귀·서비스 통합을 검사한다. 모의 모델 응답 기반 검사는 실제 이미지 인식 정확도로 집계하지 않는다.
- `python3 supabase/tests/run-account-merge-db-checks.py`: 실제 PostgreSQL에서 소유권·권한·동시 중복·재시도·교체·계정 통합을 검사한다. 로컬 Vault stub은 계약·접근·재사용 검사이며 암호화 검증이 아니다.
- iOS `OiFlowChecks`: summary 하위 호환·판정 충돌 거부·공식 링크 안전성·결과 화면을 검사한다. 충분 문자·약정·조작·중복·구형 응답을 기준/소형/대형/접근성 크기로 캡처한다.
- `python3 supabase/tests/donation-evidence.live.py --defer-account-cleanup --sample-image <사용자가 승인한 이미지 경로>`: 기존 CLI 인증을 프로세스 메모리에서만 사용한다. 한 개의 격리 테스트 계정으로 비공개 업로드·제출·실제 모델 응답·중복 판정을 확인한다. 호출 제한을 준수하고 글 작성 권한이 생성되지 않는지 확인한 뒤, 정확히 생성한 파일·신청을 정리한다. 기존 계정 연결의 삭제 제한 때문에 연결된 DB 도구로 해당 테스트 계정의 빈 self-membership만 제거한 후 `python3 supabase/tests/donation-evidence.live.py --cleanup-account`로 계정 삭제·404를 확인한다. 공개적인 계정 삭제 권한이나 스키마 제약을 완화하지 않는다. 원본/키/모델의 개인정보 응답을 파일이나 로그에 저장하지 않는다.

최종 실행 수치·배포 버전·실모델 결과는 PR의 검증 결과에 기록한다. 소수 사례의 통과를 전체 증빙의 탐지 정확도 보장으로 확대하지 않는다.


보안 점검에서 신규 장부는 private schema·RLS·권한 회수로 일반 사용자 접근을 막았으며, 키 getter/등록 RPC의 service-role 전용 권한을 원격 조회로 재확인했다. [RLS 정책 없음 안내](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy)는 이 의도적인 deny-all 장부에 INFO로 추가된다. 기존 공개 테이블/함수와 비밀번호 보호 관련 경고는 이번 변경 전후 동일하며, 이 작업에서 임의로 변경하지 않았다.
