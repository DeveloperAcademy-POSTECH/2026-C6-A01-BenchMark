# 오이·카드 커스텀 로딩 최적화 · 2026-11-16 · #390

사용자 확정 범위는 STEP 3/4 로딩 단축이며, 기존 의상·사진 편집·회전·카드 내보내기·초안 저장과 캐릭터 화질·투명 배경을 보존한다. 서버 계약이나 리소스 해상도는 변경하지 않는다.

## 구현

- STEP 2 이야기를 작성하는 동안 선택된 모델 하나만 미리 준비한다. 열 상태가 serious 이상이면 미리 준비하지 않는다.
- `OiWardrobeModelCache`는 의상·카드 렌더러가 사용할 마지막 원본 엔티티 하나만 보관한다. 동시 요청은 같은 로딩을 기다리고, 서로 다른 모델은 직렬로 로딩한다. 호출자별 취소를 확인하고 실패는 캐시하지 않는다. 메모리 경고·백그라운드·열 상태 변화에서 비우며, 비우기 전에 시작한 작업은 캐시를 다시 채우지 못한다. critical 상태에서는 원본을 보관하지 않는다.
- 각 렌더러는 독립적인 엔티티 복제본을 사용한다. 공유하는 것은 원본 메시·텍스처 리소스이며 카메라·앵커·ARView·사용자가 꾸민 재질을 공유하지 않는다. 지도·현장 AR의 기존 직접 로딩 경로는 유지한다.
- STEP 3은 정확히 일치하는 정면 초상 또는 해당 세트의 번들 썸네일을 준비 중에 표시한다. 3D가 준비되면 원래 모델을 표시한다. 썸네일을 완성된 카드나 저장 이미지로 사용하지 않는다.
- `OiPortraitImages` 액터는 PNG 인코딩·복원·투명도 검사·매트 합성을 하나씩 수행한다. 마지막 키·원본 PNG 바이트와 일치하는 디코딩 이미지 하나를 재사용한다. 크기를 줄이거나 JPEG로 바꾸지 않는다.
- STEP 4는 저장된 PNG의 검증이 끝날 때까지 새 캡처 장면을 만들지 않는다. 일반 카드 미리보기에서는 유효한 PNG이면 재캡처하지 않고, 불투명하거나 오래된 키이면 기존처럼 다시 생성한다. 결과를 적용할 때 현재 의상·각도 키와 취소 상태를 확인한다.
- 흑백 두 번 촬영해 알파를 복원하는 방식은 유지한다. 8-bit sRGB 변환값 256개를 재사용하고 세 채널의 중앙값을 배열 생성 없이 계산한다. 원래 매트 수식의 픽셀 해시 회귀 검사로 검정 눈·입과 반투명 경계를 보존한다.
- 카드 배치 편집에서 회전이 끝나면 숨겨진 캡처 장면을 해제한다. 화면에 보이는 회전용 장면은 유지하고 다음 각도 변경 시 캡처 장면을 다시 만든다.

## 실기기 측정 조건

Jun iPhone(iPhone 17, iOS 26.7.3), Release, 332×472pt / 996×1416px. 사용자 초안을 읽거나 저장하지 않는 임시 진단 화면에서 실제 `OiWardrobeScene.update` → `cardPortrait` → PNG 저장·복원 경로를 실행했다. 흰티+반바지 → 운동복 → 같은 운동복 → 흰티+반바지 순서로 각 단계 사이 3초 대기했다. 최초 기준과 최적화 빌드에서 Instruments Activity Monitor를 각각 60초 기록했다. 진단 화면과 진입 코드는 최종 앱에서 제거했다.

초기 기준 측정은 이미 serious 열 상태였으므로 열 성능 개선의 근거로 삼지 않는다. 기기가 식은 뒤 기준 시간 측정을 다시 수행했고, 정상 열 상태의 시간 기준과 최적화 결과를 비교한다. 기준 빌드 사본 재설치 뒤 Instruments가 프로세스를 찾지 못해 정상 열 상태 기준의 CPU·메모리 재측정은 확보하지 못했다. 아래 시간은 해당 렌더링 경로의 단일 시나리오 측정이며 전체 화면 전환의 통계적 p95나 장시간 배터리·발열 보장은 아니다.

| 항목 | 기존 | 최적화 |
| --- | ---: | ---: |
| 운동복 첫 준비 | 484ms | 516ms |
| 같은 운동복 다시 준비 | 482ms | 60ms |
| 카드 PNG 생성(4회 범위) | 1,456~1,805ms | 1,009~1,061ms |
| 생성 직후 PNG 검증·복원 | 3.16~3.64ms | 0.011~0.016ms |

원본 모델의 첫 로딩 자체는 줄이지 않았다. STEP 2 미리 준비·즉시 미리보기·동일 모델 재사용으로 대기 구간을 줄인다. 카드 시간에는 장면 준비·렌더 대기·흑백 촬영·매트 처리·PNG 인코딩이 포함된다. 저장된 유효 PNG로 재진입할 때는 이 캡처 경로를 생략한다.

흰티+반바지 PNG는 전후 모두 654,838byte, 운동복은 794,300byte이며 996×1416px·투명도 검사가 일치했다. 별도 수식 회귀 검사는 기존 매트 결과와 픽셀 SHA256이 일치한다.

최적화 빌드의 60초 기록에서 최대 physical footprint는 **394.3MiB**, 마지막 값은 **218.7MiB**, CPU 평균은 **4.89%**(기록 도구 기준), 순간 최대는 **43.44%**였다. 열 상태는 전체 기록에서 **Nominal**이었다. 초기 serious 상태 기준의 최대 메모리는 360.3MiB·마지막 220.5MiB였으나, 열 상태와 프로파일러 연결 시점이 달라 메모리·CPU 개선률로 비교하지 않는다. CPU 평균에는 모델 준비·카드 생성 뒤 유휴 구간도 포함한다. 장시간 사용에서 발열이 없다는 뜻은 아니다.

## 검증

- 캐시의 동시 로딩 공유·취소 격리·복제본 변경 격리·단일 원본 유지·실패 복구·로딩 중 캐시 폐기.
- PNG 원본 바이트·해상도·알파 유지, 불투명 PNG 거부, 각도별 키 분리·폐기 후 복원.
- 기존 검정 배경 초안 재생성 시 본문·사진·의상·배치 보존.
- 의상 사진 편집 재진입 복원, 실제 카드 캡처의 투명 모서리와 불투명 검정 눈·입.
- 카드 배치 회전 후 두 번째 투명 캡처, STEP 3/4 화면 캡처, 기본 8개 의상의 피부 재질·키 150cm·렌더링.

관련 자동 검사 12개가 모두 통과했고, 8개 기본 의상의 피부 PBR 텍스처·법선·거칠기·높이와 실제 렌더를 확인했다. 최종 진단 코드를 제거한 Release 빌드도 통과했고 Jun iPhone에 업데이트 설치·실행했다.

일상 사용의 실제 캠퍼스 환경·장시간 발열과 배터리 소모는 추가 관찰이 필요하다. 이번 검증 중 실제 이야기·카드 요청을 제출·승인하거나 운영 DB를 변경하지 않았다.

## develop 통합 검증 · #390

최신 `develop`의 이야기 작성 수정(#384, `38b5af6`)을 충돌 없이 통합했다. 미리 준비하는 시점은 약관(STEP 1)이 아니라 이야기 작성(STEP 2)으로 맞췄다. 카드 시트 높이·빈 목록·오류·요청 영수증·계정 변경·충돌 처리와 커스텀 로딩·사진 편집·초안 재생성·회전·기본 8종 렌더링, 최신 이야기 단계 이동을 포함한 **21개 검사**가 iOS 27.2 Simulator에서 통과했다. 통합된 코드의 실기기용 Release 빌드도 통과했다. 카드 요청의 데이터 처리 함수는 기존 develop과 동일함을 대조했다.
