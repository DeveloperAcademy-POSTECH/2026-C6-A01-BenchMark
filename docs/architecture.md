## 1. 확정된 제품 경계 — 2026-10-27

오이기부는 소액 기부로 캠퍼스에 자신의 이야기를 남기고 싶은 10~30대를 대상으로 한다. 기부자와 이용자는 농부가 되어 오이·카드를 수집하고, 농부·오이 캐릭터를 옷과 아이템으로 꾸미는 경험을 기획한다. 구체적인 성장·수집·아이템 획득 규칙은 미정이다.

기부자는 운영자에게 이체 내역 등 증빙을 제출하고 **수동 검토로 글 작성 승인을 받은 뒤** 스토리를 작성한다. 오이는 3D 캠퍼스 위치 및 실제 위도·경도와 연결하며 현장 AR에서 터치하면 동일한 스토리가 열리도록 기획한다. 실제 위치 기반 AR 배치·증빙 제출·승인·꾸미기 시스템은 현재 지도 UI 구현과 구분한다.

앱과 팀이 직접 기부금을 수납·전달하지 않는 원칙을 유지한다. 정식 수납처의 기존 절차를 이용하며 실제 안내할 기부처·공식 경로와 운영 기준은 확정이 필요하다. **운영자의 앱 작성 승인, 학교의 공식 납입 확인, 영수증 발급은 서로 다르다.** 외부 사이트 방문·자기보고·증빙 업로드만으로 자동 승인하지 않는다. 학교의 새 협업·API 제공·운영 승인을 가정하지 않는다.

물리적 명패 제작·부착과 NFC 설치는 새 서비스의 필수 단계에서 제외한다. 기존 코드와 과거 모델은 후속 구현에서 전환 범위를 정하고 보존·정리한다. 상세 정책과 미정 항목은 [project.md](../project.md)를 따른다.

## 2. 초기 코드 적용과 제안의 구분

2026-10-11 이슈 #56에서 초기 구조를 적용했다.

- AppContainer가 실제 파일럿용 미연결 Repository와 명시적 Preview 구현을 구분한다.
- RootTabView가 각 탭의 NavigationStack과 독립 카메라 버튼을 소유하고 HomeView는 홈 콘텐츠를 표시한다.
- AppRouter와 PublicLinkParser가 벤치·스토리 경로를 분리한다. 운영 도메인은 미정이므로 실제 앱 링크 수신은 비활성 상태다. Associated Domains·NFC 태그 배포는 아직 하지 않았다.
- 기존 모델은 Domain/Models로 이동하되 기존 Donation 등의 이름·필드는 유지했다. 기존 DonationStatus는 호환을 위해 남겼으며 새 참여 흐름은 신청·납입 확인·명패 상태를 각각 사용한다.
- Home·Participation·MyDonations 화면 상태와 Repository 인터페이스, Benches 조회·공개 링크 상세 화면을 추가했다.
- APIClient는 HTTPS·허용 호스트·HTTP 응답 검증을 위한 기반이며 실제 API 경로·DTO·토큰 저장·인증 공급자 연동은 아직 없다. 호출 전 승인된 서버와 인증 계약이 필요하다.
- 2026-10-11 홈 디자인 확인 요청에 따라 실행 앱의 홈 현황에는 DesignDemoHomeRepository의 Figma 예시를 임시 표시한다. 화면에 예시임을 표시하며 실제 학교 수치가 아니다. 나머지 미연결 저장소는 빈 목록을 반환하고 신청 저장은 실패한다. Preview 신청은 메모리 전용이며 학교 확인 대기로만 생성된다.
- 도메인·링크·중복 요청·미연결 상태 검증은 apps/ios/Tests/run-architecture-checks.sh로 실행할 수 있다.
- 검증: iOS Simulator 빌드와 위 검증 스크립트 통과. 시뮬레이터에서 홈의 기부 시작 → 참여 신청 이동, 독립 카메라 버튼의 AR 화면 진입을 확인했다. 카메라 화면은 기존 뼈대이며 실제 촬영 검증은 아니다.

운영자 웹·학교 확인 연동·서버 저장·로그인·실제 지도는 아직 없다. 이슈 #58에서 ARTest 기반 캐릭터 카메라 세션·배치를 통합했다. 상세 범위와 실기기 검증 상태는 apps/ios/docs/ar-camera.md를 따른다. 아래 설계의 미적용 항목과 정책은 제안이며 이 코드가 서비스 완성을 의미하지 않는다.

## 3. 전체 서비스 구조

```text
iOS 앱 ──────────┐
                 ├── 서버 API ── 데이터베이스
운영자 웹 ───────┘       └── 사진·콘텐츠 저장소

iOS 앱 ── 외부 안내 ── POSTECH 공식 약정·납입 절차
                              └── 합의된 확인 절차 ── 운영자·서버
```

학교가 약정·결제·영수증·환불을 처리한다. 서버는 앱의 신청·공개 콘텐츠·진행 상태를 관리한다. 승인된 수동 확인부터 시작할 수 있으며, 제공 가능한 정보·식별 방식·확인 담당자·주기는 학교와 협의해야 한다.

## 4. iOS 구조 제안

기능별 MVVM과 Repository 인터페이스를 사용한다. 단순 표시 화면은 View만으로 시작하고 비동기 작업이나 복잡한 상태가 생기면 ViewModel을 추가한다. 초기부터 별도 모듈·프레임워크나 모든 작업용 UseCase를 의무적으로 만들지 않는다.

```text
OiDonation/
├── App/                 # 앱 진입, 서비스 연결, 루트 탭, 링크 라우팅
├── Features/
│   ├── Home/
│   ├── Stories/
│   ├── Benches/
│   ├── Participation/
│   ├── MyDonations/
│   ├── Auth/
│   ├── Profile/
│   └── AR/
├── Domain/
│   ├── Models/
│   └── Repositories/    # 인터페이스
├── Data/
│   ├── Networking/
│   ├── DTOs/
│   └── Repositories/    # API 구현
├── Shared/
│   ├── DesignSystem/
│   ├── Components/
│   └── Utilities/
└── Resources/           # 에셋·3D 모델; 기존 리소스 위치는 유지 가능
```

| 계층 | 역할 |
| --- | --- |
| View | 레이아웃, 입력, 상태 표시 |
| ViewModel | 입력 검증, 작업 실행, 로딩·오류·재시도 상태 |
| Repository | 조회·저장 인터페이스; 실제 및 테스트 구현 교체 |
| APIClient | 인증 전달, 요청·응답, 공통 오류 처리 |
| 서버 | 권한 검증, 벤치 배정·신청 중복 방지, 공식 진행 상태 관리 |

제안하는 의존 방향은 View → ViewModel → Repository 인터페이스다. Data 구현은 Domain 인터페이스를 구현하고 AppContainer가 실제·테스트 구현을 연결한다. Domain은 SwiftUI나 서버 DTO에 의존하지 않는다. 서버 데이터는 DTO에서 앱 모델로 변환한다.

## 5. 데이터 모델과 상태

| 모델 제안 | 의미 |
| --- | --- |
| User | 로그인 사용자; 공개 프로필과 필요한 개인 정보 구분 |
| Bench | 승인된 기존 벤치, 위치, 공개·배정 가능 상태 |
| ParticipationApplication | 벤치 선택, 이야기·문구, 참여 신청 |
| DonationRecord | 학교에서 확인한 기부 기록; 앱 신청과 연결 방식 협의 필요 |
| Plaque | 승인 문구, 제작·부착·운영 상태 |
| Story | 공개 이야기, 사진, 플레이리스트, 공개 여부 |
| Reaction | 공감·감사 메시지, 신고·숨김 상태 |

기존 Donor와 User의 역할, Donation과 위 모델의 관계는 모델 담당자와 합의 후 결정한다. 한 신청에 여러 기부 기록이나 명패를 연결할 수 있는지 등 관계·수량은 명패 정책 확정 후 설계한다.

상태는 하나의 긴 enum으로 합치기보다 다음 영역을 구분하는 방향을 제안한다.

- 신청: 초안 → 제출 → 검토 → 승인 / 수정 요청 / 취소
- 납입 확인: 확인 대기 → 학교 확인 완료
- 명패: 제작 대기 → 제작 중 → 부착 완료

이는 초기 초안이다. 부분 납입·취소·환불·명패 재제작은 학교 절차를 확인해 전이 규칙을 추가한다. 신청 승인이 제작 시작이나 납입 완료를 의미하지 않는다. 명패 제작 가능 조건도 학교 및 팀 합의가 필요하다.

공식 상태의 원본은 서버에 두고, 사용자 클라이언트가 납입 확인 완료를 직접 수정하지 못하게 한다. 운영자 변경에는 변경자·시각·근거를 기록하며 민감한 증빙은 일반 공개 응답에서 제외한다.

## 6. 화면 이동과 탭바

전체 앱에서는 RootTabView가 홈·내 기부·후원·벤치지도와 별도 카메라 버튼을 관리하는 방향을 제안한다. HomeView는 홈 콘텐츠에 집중한다. 홈 전체 미리보기는 루트 화면으로 구성한다. 현재 홈 구현을 즉시 재구성하라는 지침은 아니다.

각 탭은 자신의 NavigationStack과 경로를 유지한다. AppRouter는 벤치·스토리 ID 기반 링크를 해석하고, 미공개·삭제 콘텐츠와 로그인 필요 상태를 처리한다. 로그인 없이 공개 이야기를 탐색하고 참여 신청 등 필요한 시점에 로그인하도록 설계한다.

## 7. NFC와 AR

NFC에는 공개 벤치 URL을 기록한다. 개인정보·로그인 토큰은 넣지 않는다. 앱 설치 여부에 따른 웹 안내와 앱 링크 처리를 함께 설계한다. URL 형식과 운영 도메인은 미정이다. NFC는 기부 확인 수단이 아니다.

AR은 카메라 권한, 세션, 캐릭터 선택, 사진 합성을 독립 기능으로 관리한다. 화면 진입·종료에 맞춰 세션을 시작·해제하고 권한 거절 및 기기 미지원 상태를 표시한다. 촬영 사진은 기본적으로 기기에 저장하며 서버 업로드는 사용자 선택과 별도 정책이 필요하다.

## 8. 서버·운영자·인증

운영자 최소 기능은 신청·문구 검토, 학교 확인 결과 연결, 명패 제작·부착 상태 변경, 벤치 공개 관리, 신고 콘텐츠 처리다. 기존 웹·서버 구조를 조사하고 재사용할 부분을 결정한다. 기술 스택을 이 문서만으로 새로 확정하지 않는다.

사용자·운영자 권한과 상태 전이는 서버에서 검증한다. 참여 신청 재전송은 중복 생성되지 않도록 처리하고 벤치 배정 경쟁은 서버 트랜잭션·제약으로 해결한다. 업로드 크기·형식, 공개 범위와 삭제 정책을 정의한다.

로그인 공급자, 서버 토큰 발급 방식과 세션 갱신은 API 계약에서 합의한다. 앱 인증 토큰은 Keychain 등 적절한 저장소에 보관하고, 서버 비밀키는 앱과 저장소에 포함하지 않는다. 학교에서 이미 수집하는 결제·개인정보는 앱에서 중복 수집하지 않는다.

행동 로그에서 공식 사이트 이동, 신청 제출, 학교 확인 완료를 구분한다. 개인정보·이야기 본문·사진·토큰은 분석 로그에 넣지 않는다. 외부 사이트의 실제 납입 전환율은 연동 없이 앱 로그만으로 측정할 수 없다.

## 9. 개발 환경과 검증

공식 배포 계정·Bundle ID는 팀이 정하고 개인 개발 서명은 로컬 설정으로 분리하는 방향을 검토한다. 인증서 개인 키·p12·토큰과 개인 설정은 커밋하지 않는다. 개발·운영 서버 주소와 각 앱 ID에 연결된 기능 설정도 구분한다.

검증 우선순위는 신청 입력·재시도·중복 방지, 납입 상태 오표시 방지, 운영자 권한, 벤치 배정 충돌, 링크 라우팅이다. Repository 테스트 구현으로 로딩·빈 상태·오류를 재현하고 화면 빌드 및 주요 흐름을 확인한다. AR·NFC는 실제 기기에서 추가 검증한다.

## 10. 팀 협업 방식

문서의 역할을 구분한다.

- project.md: 제품 목적, 확정 기획, 미정 정책
- docs/architecture.md: 설계 제안·합의·현황
- AGENTS.md: 읽을 문서와 확정된 작업 규칙
- GitHub Issues: 담당 기능, 범위, 완료 조건

팀원은 최신 develop에서 이슈별 브랜치를 만든다. 먼저 모델·상태 이름, API 요청·응답·오류, 화면 이동 ID, 디자인 토큰을 합의하고 기능별 작업을 나눈다. 공통 파일 변경은 담당자와 공유한다. 설계 변경 시 코드와 관련 문서를 같은 PR에서 수정한다.

AI 작업 요청 예시:

> AGENTS.md, project.md, docs/architecture.md와 이슈 #번호를 읽고 작업해줘. 확정 사항과 검토 중 제안을 구분하고 현재 이슈에서 합의된 범위만 구현해줘.
