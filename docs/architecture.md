## 1. 확정된 제품 경계 — 2026-11-08 / #234, 2026-11-09 / #258

오이기부에서는 이용자가 농부가 되어 캠퍼스에 이야기를 남기고, 오이·카드를 수집하며, 농부·오이를 꾸민다. 구체적인 성장·수집·아이템 획득 규칙은 미정이다.

로그인한 사용자는 기부나 증빙 없이 꾸민 오이를 이 기기의 계정별 지도에 배치한다. 다른 사람에게 보여 주려면 이야기·사진·오이·카드의 공개 검토를 요청한다. DB는 로그인·소유권·서버 작성 상태를 확인하고 운영자만 공개를 승인한다. 지도·현장 AR의 공개 이야기에는 승인된 외형을 적용하고, 카드 화면에는 검토된 카드 이미지를 표시한다. 승인 이미지가 없는 예전 이야기에는 기존 디자인을 사용한다.

공식 수납처를 안내하며 앱과 팀은 직접 기부금을 수납하거나 전달하지 않는다. #258은 기부 증빙 신규 접수·재제출·운영자 검토와 사용자·운영자 AI 호출을 종료한다. 이전에 접수한 자료와 작성 승인 연결은 비공개 이력으로 남기고 탈퇴 시 삭제한다. 콘텐츠 공개 검토·신고·차단과 별도 학교 자료 분석은 유지한다. 구형 앱 차단과 배포 순서는 [기부 증빙 종료](donation-evidence-retirement.md)를 따른다.

물리적 명패 제작·부착과 NFC 설치는 새 서비스의 필수 단계에서 제외한다. 기존 코드와 과거 모델은 후속 구현에서 전환 범위를 정하고 보존·정리한다. 상세 정책과 미정 항목은 [project.md](../project.md)를 따른다.

## 2. 초기 코드 적용과 제안의 구분

2026-10-11 이슈 #56에서 초기 구조를 적용했다.

- Home·Participation·MyDonations 화면 상태와 Repository 인터페이스, Benches 조회·공개 링크 상세 화면을 추가했다.

## 3. 전체 서비스 구조

```text
iOS 앱 ──────────┐
                 ├── 서버 API ── 데이터베이스
운영자 웹 ───────┘       └── 사진·콘텐츠 저장소

iOS 앱 ── 외부 안내 ── POSTECH 공식 약정·납입 절차
                              └── 합의된 확인 절차 ── 운영자·서버
```

학교가 약정·결제·영수증·환불을 처리한다. 서버는 앱의 신청·공개 콘텐츠·진행 상태를 관리한다. 승인된 수동 확인부터 시작할 수 있으며, 제공 가능한 정보·식별 방식·확인 담당자·주기는 학교와 협의해야 한다.

## 4. iOS 구조 제안

기능별 MVVM과 Repository 인터페이스를 사용한다. 단순 표시 화면은 View만으로 시작하고 비동기 작업이나 복잡한 상태가 생기면 ViewModel을 추가한다. 초기부터 별도 모듈·프레임워크나 모든 작업용 UseCase를 의무적으로 만들지 않는다.

```text
OiDonation/
├── App/                 # 앱 진입, 서비스 연결, 루트 탭, 링크 라우팅
├── Features/
│   ├── Home/
│   ├── Stories/
│   ├── Benches/
│   ├── Participation/
│   ├── MyDonations/
│   ├── Auth/
│   ├── Profile/
│   └── AR/
├── Domain/
│   ├── Models/
│   └── Repositories/    # 인터페이스
├── Data/
│   ├── Networking/
│   ├── DTOs/
│   └── Repositories/    # API 구현
├── Shared/
│   ├── DesignSystem/
│   ├── Components/
│   └── Utilities/
└── Resources/           # 에셋·3D 모델; 기존 리소스 위치는 유지 가능
```

| 계층 | 역할 |
| --- | --- |
| View | 레이아웃, 입력, 상태 표시 |
| ViewModel | 입력 검증, 작업 실행, 로딩·오류·재시도 상태 |
| Repository | 조회·저장 인터페이스; 실제 및 테스트 구현 교체 |
| APIClient | 인증 전달, 요청·응답, 공통 오류 처리 |
| 서버 | 권한 검증, 벤치 배정·신청 중복 방지, 공식 진행 상태 관리 |

제안하는 의존 방향은 View → ViewModel → Repository 인터페이스다. Data 구현은 Domain 인터페이스를 구현하고 AppContainer가 실제·테스트 구현을 연결한다. Domain은 SwiftUI나 서버 DTO에 의존하지 않는다. 서버 데이터는 DTO에서 앱 모델로 변환한다.

## 5. 데이터 모델과 상태

| 모델 제안 | 의미 |
| --- | --- |
| User | 로그인 사용자; 공개 프로필과 필요한 개인 정보 구분 |
| Bench | 승인된 기존 벤치, 위치, 공개·배정 가능 상태 |
| ParticipationApplication | 벤치 선택, 이야기·문구, 참여 신청 |
| DonationRecord | 학교에서 확인한 기부 기록; 앱 신청과 연결 방식 협의 필요 |
| Plaque | 승인 문구, 제작·부착·운영 상태 |
| Story | 공개 이야기, 사진, 플레이리스트, 공개 여부 |
| Reaction | 공감·감사 메시지, 신고·숨김 상태 |

기존 Donor와 User의 역할, Donation과 위 모델의 관계는 모델 담당자와 합의 후 결정한다. 한 신청에 여러 기부 기록이나 명패를 연결할 수 있는지 등 관계·수량은 명패 정책 확정 후 설계한다.

상태는 하나의 긴 enum으로 합치기보다 다음 영역을 구분하는 방향을 제안한다.

- 신청: 초안 → 제출 → 검토 → 승인 / 수정 요청 / 취소
- 납입 확인: 확인 대기 → 학교 확인 완료
- 명패: 제작 대기 → 제작 중 → 부착 완료

이는 초기 초안이다. 부분 납입·취소·환불·명패 재제작은 학교 절차를 확인해 전이 규칙을 추가한다. 신청 승인이 제작 시작이나 납입 완료를 의미하지 않는다. 명패 제작 가능 조건도 학교 및 팀 합의가 필요하다.

공식 상태의 원본은 서버에 두고, 사용자 클라이언트가 납입 확인 완료를 직접 수정하지 못하게 한다. 운영자 변경에는 변경자·시각·근거를 기록하며 민감한 증빙은 일반 공개 응답에서 제외한다.

## 6. 화면 이동과 탭바

전체 앱에서는 RootTabView가 홈·내 기부·후원·벤치지도와 별도 카메라 버튼을 관리하는 방향을 제안한다. HomeView는 홈 콘텐츠에 집중한다. 홈 전체 미리보기는 루트 화면으로 구성한다. 현재 홈 구현을 즉시 재구성하라는 지침은 아니다.

각 탭은 자신의 NavigationStack과 경로를 유지한다. AppRouter는 벤치·스토리 ID 기반 링크를 해석하고, 미공개·삭제 콘텐츠와 로그인 필요 상태를 처리한다. 로그인 없이 공개 이야기를 탐색하고 참여 신청 등 필요한 시점에 로그인하도록 설계한다.

## 7. NFC와 AR

NFC에는 공개 벤치 URL을 기록한다. 개인정보·로그인 토큰은 넣지 않는다. 앱 설치 여부에 따른 웹 안내와 앱 링크 처리를 함께 설계한다. URL 형식과 운영 도메인은 미정이다. NFC는 기부 확인 수단이 아니다.

AR은 카메라 권한, 세션, 캐릭터 선택, 사진 합성을 독립 기능으로 관리한다. 화면 진입·종료에 맞춰 세션을 시작·해제하고 권한 거절 및 기기 미지원 상태를 표시한다. 촬영 사진은 기본적으로 기기에 저장하며 서버 업로드는 사용자 선택과 별도 정책이 필요하다.

## 8. 서버·운영자·인증

운영자 최소 기능은 신청·문구 검토, 학교 확인 결과 연결, 명패 제작·부착 상태 변경, 벤치 공개 관리, 신고 콘텐츠 처리다. 기존 웹·서버 구조를 조사하고 재사용할 부분을 결정한다. 기술 스택을 이 문서만으로 새로 확정하지 않는다.

사용자·운영자 권한과 상태 전이는 서버에서 검증한다. 참여 신청 재전송은 중복 생성되지 않도록 처리하고 벤치 배정 경쟁은 서버 트랜잭션·제약으로 해결한다. 업로드 크기·형식, 공개 범위와 삭제 정책을 정의한다.

로그인 공급자, 서버 토큰 발급 방식과 세션 갱신은 API 계약에서 합의한다. 앱 인증 토큰은 Keychain 등 적절한 저장소에 보관하고, 서버 비밀키는 앱과 저장소에 포함하지 않는다. 학교에서 이미 수집하는 결제·개인정보는 앱에서 중복 수집하지 않는다.

행동 로그에서 공식 사이트 이동, 신청 제출, 학교 확인 완료를 구분한다. 개인정보·이야기 본문·사진·토큰은 분석 로그에 넣지 않는다. 외부 사이트의 실제 납입 전환율은 연동 없이 앱 로그만으로 측정할 수 없다.

## 9. 개발 환경과 검증

공식 배포 계정·Bundle ID는 팀이 정하고 개인 개발 서명은 로컬 설정으로 분리하는 방향을 검토한다. 인증서 개인 키·p12·토큰과 개인 설정은 커밋하지 않는다. 개발·운영 서버 주소와 각 앱 ID에 연결된 기능 설정도 구분한다.

검증 우선순위는 신청 입력·재시도·중복 방지, 납입 상태 오표시 방지, 운영자 권한, 벤치 배정 충돌, 링크 라우팅이다. Repository 테스트 구현으로 로딩·빈 상태·오류를 재현하고 화면 빌드 및 주요 흐름을 확인한다. AR·NFC는 실제 기기에서 추가 검증한다.

## 10. 팀 협업 방식

문서의 역할을 구분한다.

- project.md: 제품 목적, 확정 기획, 미정 정책
- docs/architecture.md: 설계 제안·합의·현황
- AGENTS.md: 읽을 문서와 확정된 작업 규칙
- GitHub Issues: 담당 기능, 범위, 완료 조건

### 2026-11-03 확대 단계별 지도 이름표

`CampusMapLabels`는 Home의 `CampusExploreScene` 캔버스 위에 터치를 가로채지 않는 UIKit 이름표를 투영한다. 전체 지도는 `CampusRegion`의 6개 구역과 표시용 RIST 실험동 구역을, 확대 화면은 기존 이름 있는 건물 82개와 RIST 실험동 8개 중 화면에 충분히 크게 보이는 건물을 대상으로 한다. POI/실내 시설명이 아닌 건물 ID별 한 이름을 사용한다. 지붕 높이와 외곽선 안의 점에 고정하며, 오목한 외곽선은 내부 후보점으로 보정한다.

화면 높이·카메라 FOV·거리에 따른 투영 밀도로 구역/건물 단계를 전환한다. 진입 6.5pt/unit, 이탈 5.3pt/unit의 차이를 두어 미세 핀치에서 깜박임을 줄인다. 개별 건물의 화면 외곽 크기도 검사하며, 주요 건물 우선의 안정된 순서로 이름 간 충돌을 제외한다. 이름표는 흰 테두리의 작은 녹색 글씨이며 숫자 패널, 홈 버튼, 헤더, 목록 아래에 겹치지 않게 한다. 확장 목록에서는 숨긴다. 카메라 갱신과 렌더러 복귀 때 위치를 다시 투영하고, 이름 표시가 없는 요약 지도나 실제 AR 배치 좌표·크기에는 영향을 주지 않는다.

`campus-data.json`의 선택적 `buildingLabelGroups`는 검토한 건물 ID들을 공통 구역명에 연결한다. 원본 건물명이 있으면 우선 사용하고, 빈 이름만 이 메타데이터로 보완한다. RIST 실험동 8개에는 공통 이름을 사용하며 개별 동 번호를 추측하지 않는다. 표시용 구역에는 오이 수 버튼을 만들지 않고 서버의 지역 ID·스토리 분류를 변경하지 않는다. 구역 중심이 화면 밖에 있으면 보이는 구성 건물의 지붕 위치에서 이름표 후보를 찾고, 가장자리와 기존 마커와의 충돌을 피한다. 메타데이터가 없는 기존 지도도 디코딩된다.

### 기본 지도 구역별 숫자 표식

## 세트 의상 사진 합성 — 2026-11-06, #172

세트 전반의 주름 끊김을 수정하기 위해 `OiWardrobeAsset`의 세트·과잠 경로는 원본 UV 색상 텍스처에 사진을 합성한다. 별도 오프셋 메쉬를 추가하지 않는다. 의상별 좌표 맵은 오프라인 생성하고 `OiCostumePhotoBaker`가 현재 모델 데이터만 캐시하여 메인 스레드 밖에서 처리한다. 원래 물성·메쉬·150cm 치수와 초안 사진 저장 계약은 유지한다. 사진을 지우거나 취소하면 보관한 원본 재질을 복원하며, 취소된 비동기 결과는 미리보기에 반영하지 않는다. 세부 적용 범위·자산 갱신 규칙·검증은 [옷장 문서](wardrobe-customization.md#세트-사진의-주름-끊김-수정--172-2026-11-06)를 따른다.

프레임이 엉덩이 쪽으로 내려가는 후속 제보에 따라 세트는 의상별로 검토한 앞·뒷면 목선에서 12cm 아래를 윗변으로 사용한다. 프레임 높이는 몸통 길이에 맞춰 14~22cm로 제한한다. 기준 높이는 `tools/wardrobe/photo-print-anchors.json`의 미터 단위 값이다. 기존 세트 사진은 읽을 때 새 프레임으로 재배치하고 완료 시 `frameRevision: 2`를 저장해 중복 이동을 막는다. 취소 시 원본 초안·사진 바이트는 보존한다. 개별 의상은 #177 결정에 따라 프레임과 자동 재배치를 사용하지 않는다.


사진 이동 중 둥근 잘림이 사진을 따라가는 실기기 제보에 대응해, 편집 화면의 이미지 뷰 마스크를 `OiPhotoLayerCanvas`의 고정 좌표 클립으로 교체했다. 캔버스 프레임을 먼저 설정하고 각 원본 사진을 독립 컨텍스트에서 변환해 그린다. 원본/저장 형식과 3D 합성 경로는 유지하며, 앞·뒤 다중 사진의 화면 픽셀을 출력 아틀라스와 비교하는 회귀 검사를 추가했다. 실기기 제보와 시뮬레이터 검증의 범위는 옷장 문서에 기록한다.

세트 편집기에는 전체 정사각형 UV 패널 대신 둥근 인쇄 영역만 확대해 표시한다. `OiPhotoPrintViewport`가 화면 크기를 원본 패널 좌표로 환산하고 사진 선택/드래그도 같은 변환을 사용한다. 원본 좌표계·저장 형식·3D 프레임은 변경하지 않는다. 빈 상태 안내는 프레임 밖에 둔다.

## 작성한 오이의 지도 배치 — 2026-11-08 / #239

4단계 카드 꾸미기의 **완료**는 초안에 저장된 좌표와 의상으로 `CampusExploreScene`의 배치 미리보기를 연다. **내 지도에 배치하기**는 계정별 `OiLocalDraft`에 확인한 위치·이름·높이·방향을 저장하고 홈 지도의 해당 위치를 연다. **공개 검토 요청**에서 작성자가 제출을 확정하면 이야기와 사진을 서버에 저장하고 검토를 요청한다.

공개 검토 전 확인 화면은 이야기 본문·첨부 사진과 오이·의상 사진을 구분한다. 현재 착용 중인 의상에 사용한 사진만 앞면과 뒷면을 표시해 보여 준다. 2026-11-09부터 작성자가 꾸민 카드 한 장을 미리 보고 검토를 요청한다. 지도 렌더러는 검토 화면을 열 때 해제하고 돌아오면 현재 배치 상태를 복원한다.

배치 미리보기에서 한 손가락 드래그는 화면에서 발 위치를 옮긴 뒤 지형과 교차하는 유효 좌표를 고른다. 핀치와 두 손가락 회전은 지도 카메라를 고정한 채 오이의 높이와 방향을 변경한다. 두 손가락을 쓴 제스처는 손가락을 모두 뗄 때까지 위치를 잠그고, 제스처가 끝나면 위치·구역·높이·방향을 계정별 초안에 저장한다. `save_story`는 `height_meters`와 `heading_degrees`를 기존 위치와 함께 기록하며, 공개 이야기의 상세·주변 AR은 동일한 필드를 사용한다. 지도 모델의 표시 배율과 카메라에 표시하는 실제 높이를 구분한다.

홈 지도는 현재 계정의 내 지도 배치와 기존 검토 대기 배치를 작성자 전용 레이어에 표시한다. 확인한 기기 위치를 우선하며 기존 검토 대기 기록은 서버 위치를 사용한다. 같은 이야기 ID로 계정별 초안의 의상·색상·사진을 찾고 전체 지도에서도 `OiWardrobeAsset`으로 조립한다. 기기에 저장한 외형이 없으면 기본 3D 오이를, 모델을 읽지 못하면 위치 라벨을 표시한다. 계정 전환 시 레이어를 지우고 삭제된 배치는 목록에서 제외한다. 공개 이야기와 ID가 겹치면 작성자 지도에서 마커 하나만 표시한다. 공개 검색·개수·AR은 공개 승인된 이야기에서 계산한다.

2026-11-09 후속: 작성자 지도에서 이름과 상태는 배경 없이 밝은 그림자를 넣은 두 줄로 표시한다. 지도를 움직일 때 회전·크기가 반영된 모델 경계를 화면에 투영해 라벨을 캐릭터 위에 배치한다. 모델을 읽기 전에는 저장한 위치를 기준으로 표시한다.
