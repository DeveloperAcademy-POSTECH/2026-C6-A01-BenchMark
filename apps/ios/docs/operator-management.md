- `OiOperatorStoryModel`은 상세 조회·처리 중·확정 응답·동기화 경고·재조회 필요 상태를 소유한다. 상세는 서버에서 이야기와 첨부 사진을 다시 조회하고, 제목·본문·상태·오이 이름·작성자 닉네임·등록일·주제·감정·구역·위경도를 표시한다. 사진은 기존 5분 서명 URL과 사진 로딩/재시도 컴포넌트를 재사용한다.

- 서버 확정 응답을 받으면 상세와 목록 필터, 공용 공개 이야기 상태를 먼저 갱신한다. 후속 공용 목록 동기화만 실패했다면 성공과 동기화 경고를 함께 표시하고 재조회 전 추가 결정을 차단한다. 상세 재조회로 확인한 최신 상태도 부모 목록에 반영한다.

## 청크 3: 기부 증빙 검토 (2026-11-04)

- 진입: 운영자 관리 → 기부 증빙 검토. `OiOperatorEvidenceListView`와 목록 모델이 검토 대기 / 작성 승인 / 보완 요청 / 반려 / 승인 취소 / 전체 필터를 제공한다. draft는 제외하고 제출 시각·ID 역순으로 기존 페이지 조회를 재사용한다.
- 상세는 접수 번호·제출자·제출/검토 시각·검토 의견·해당 증빙의 작성 승인을 새로 조회한다. 증빙 이력·AI 참고 분석·감사 기록 화면은 후속 청크다. 일반 사용자 증빙 제출 경로는 재노출하지 않는다.
- 원본은 인증된 `oi-evidence` 경로로 직접 내려받는다. 임시 URLSession의 디스크 캐시·쿠키 저장을 끄고 앱 메모리에서만 JPEG/PNG 또는 암호 없는 PDF를 표시한다. 외부 앱·서명 URL·공유·파일 저장을 사용하지 않는다. 10MiB를 초과하거나 형식/렌더링이 잘못된 파일은 열람을 거절한다. 이미지 표시용 디코딩은 최대 2,048px로 축소한다.
- 다운로드 전후에 현재 제출 스냅샷을 비교하고 서버 운영 권한을 재검사한다. 원본 경로의 storage_owner_id/요청 ID를 검증하므로 계정 통합 전 원본의 소유 경로도 보존한다. 계정 변경·재인증·권한 회수·비활성화 시 원본을 닫고 화면 메모리의 참조를 해제한다.
- 원본을 실제로 열고 ‘원본 확인 완료’를 누른 현재 스냅샷에 대해서만 검토 버튼을 활성화한다. pending에서는 승인·보완 요청·반려, approved에서는 승인 철회를 제공한다. 승인할 이야기 수에는 기본값을 두지 않고 양의 정수를 직접 입력한다. 보완 요청·반려·철회 의견은 필수이며 의견은 DB와 동일하게 유니코드 문자 2,000개 이내로 제한한다. 최소 기부액·증빙 인정 기준 등 미정 정책은 추가하지 않는다.
- 확인창에 스냅샷·결정·개수·의견을 고정한다. 중복 처리를 차단하고 충돌·응답 유실 후에는 자동 재전송 없이 최신 조회와 원본 재확인을 요구한다. 성공 후에도 다음 결정을 하려면 다시 조회한다. 확정 응답은 후속 목록 동기화 실패와 구분해 먼저 반영한다. 철회 시 해당 grant의 공개/운영/본인 이야기 캐시를 제거해 동기화 실패 시 이전 공개 상태를 노출하지 않는다.
- 새 `oi_review_evidence(p_payload jsonb)` RPC는 상태·원본 경로·제출/검토 시각을 행 잠금 안에서 비교하고 기존 `review_evidence`를 호출한다. 같은 경로로 pending 상태에 다시 제출한 경우도 이전 스냅샷은 거절한다. 기존 작성 권한 생성·철회·연결 이야기 비공개·이력·감사 기록 동작은 유지한다.
- 마이그레이션: `20261105142235_oi_guarded_evidence_review.sql`. **운영 서버에는 배포하지 않았다.** 조회/원본 열람은 기존 API를 사용하지만 실제 검토 처리는 이 마이그레이션 적용이 필요하다. RPC가 없는 서버에서는 준비되지 않았다는 안내를 표시하고 이전 RPC로 우회하지 않는다.

## 청크 4: 증빙 상태 이력·AI 참고 분석 (2026-11-04)

기존 `oi_evidence_history` 테이블·RLS·Storage와 `analyze-evidence` Edge Function의 계약을 iOS에 연결한다. 새 마이그레이션·서버 함수·승인 조건·운영 정책은 추가하지 않는다. 청크 3의 검토 조건도 이번 청크에서 변경하지 않는다. 학교 소속 증빙 AI(PR #140)는 별개다.

### 상태 변경 이력

- 증빙 상세 → 증빙 상태 변경 이력으로 진입한다. `request_id`로 한 신청만 필터하고 `recorded_at.desc,id.desc` 순서로 기존 200건 페이지 조회를 재사용한다. 로딩·보관 이력 없음·조회 실패·재시도·새로고침을 제공한다.
- 기존 테이블은 상태 변경 **직전**의 상태·원본 경로·검토 의견·검토자와 보관 시각을 저장한다. 화면도 ‘기록된 이전 상태’와 ‘보관 시각’으로 표시한다. 이를 현재 상태나 원래 제출/검토 시각으로 해석하지 않는다. 최신 상태와 의견은 기존 상세에서 확인한다.
- 각 이력의 원본은 현재 제출본 대신 그 이력의 `object_path`를 연다. 행 ID와 request_id·경로를 서버에서 대조하고 기존 storage_owner_id 경계를 검사한다. 같은 메모리 전용 이미지/PDF 뷰어를 재사용한다. 내려받은 후 이력과 운영 권한을 재확인하고 계정 세대가 달라지면 응답을 폐기한다.
- 이력의 원본 열람은 현재 제출 원본의 ‘확인 완료’를 대신하지 않는다. 이력에서 검토 결정을 실행하는 버튼은 없다.

### AI 참고 분석
